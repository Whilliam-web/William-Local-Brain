1. 能解释 FDE 为什么在 2026 年重新变热。

## 2. FDE 到底是什么

FDE 源头来自 Palantir 的 Forward Deployed Software Engineer / Forward Deployed Engineer 模式。Palantir 官方岗位描述里，FDSE 与客户并肩工作，快速理解客户最难的问题，架构并构建使用关键业务数据和 AI 的解决方案。

2025-2026 年，这个模式被 OpenAI、AWS 等 AI/云厂商重新采用：

- OpenAI FDE 团队的官方说法是：和客户合作，把研究突破转成生产系统，处在客户交付和核心平台开发之间。
- AWS 在 2026 年宣布投入 10 亿美元建立 Forward Deployed Engineering 组织，把专家嵌入客户侧，共同开发并部署 agentic AI 方案。

一句话定义：

FDE 是“工程师 + 产品经理 + 行业顾问 + 交付负责人”的复合角色，目标不是写一次性外包代码，而是在客户现场识别真实工作流、快速交付 AI 系统、把现场经验反哺产品平台。

## 3. 为什么 2026 年 FDE 变热

### 3.1 企业 AI 的瓶颈从模型能力转到落地能力

大模型能力越来越强，但企业真正部署 AI Agent 时会卡在：

- 数据不干净、不统一、权限复杂。
- 工作流是人脑经验 + 微信/Excel/ERP 的混合体。
- 业务部门讲不清需求，技术部门不了解一线细节。
- POC 能 demo，进生产就遇到安全、审计、权限、责任归因。
- Agent 出错后谁兜底、怎么赔、怎么监控仍不清楚。

这意味着“卖模型 API”不够，“卖 SaaS 座位”也不够，客户需要有人把 AI 放进真实流程里。

### 3.2 Agentic AI 让项目交付重新有产品化机会

过去企业定制开发难规模化，因为每个客户的流程都不同。Agentic AI 的变化在于：

- 许多知识劳动流程可以被拆成“感知 - 判断 - 执行 - 复核 - 记录”的通用结构。
- 不同行业表面不同，但底层会复用相似模块：数据接入、权限、知识库、任务编排、人工确认、审计日志、异常处理。
- FDE 在第一个客户处做深，真正价值在于抽象第二个、第三个客户可复用的 workflow template。

### 3.3 大厂已经把 FDE 当作 enterprise AI 的抓手

FDE 不是小团队自嗨概念。公开资料显示：

- Palantir 长期用 FDSE/FDE 模式做政府、金融、能源、供应链等复杂场景。
- OpenAI 在多个城市招聘 Forward Deployed Engineer。
- AWS 宣布 10 亿美元 FDE 组织，用于将 agentic AI 方案更快嵌入客户环境。

这给早期团队两个信号：

- 正向：客户确实需要“懂 AI + 懂现场 + 能交付”的人。
- 负向：大厂也会下场，纯通用 FDE 服务很难长期防守。

## 4. 市场上的两派观点

### 4.1 支持派：FDE 是 AI 时代的企业落地新物种

支持派认为：

- AI 不是传统 SaaS，不能只靠自助购买和配置上线。
- 企业客户的隐性流程、历史系统、数据权限、业务规则必须靠现场工程化解决。
- FDE 是最快获得真实需求、真实数据、真实 ROI 的方式。
- 现场项目不是低级交付，而是产品发现和产品化的输入。

支持派最强论点：

“AI demo 的成本趋近于零，但 PMF 和生产落地成本没有降低。谁能进入现场，谁就更接近真实 PMF。”

### 4.2 反对派：FDE 只是咨询/外包换了个高级名字

反对派认为：

- FDE 容易滑向项目制咨询，毛利低、依赖人力、不可规模化。
- 每个客户都要驻场，交付周期长，优秀工程师被消耗在客户沟通里。
- 如果产品本身不够好，FDE 会掩盖 PMF 不足。
- 客户定制越多，平台越难标准化，最后变成“高端乙方”。

反对派最强论点：

“如果第二个客户不能复用第一个客户 60% 以上的成果，这就不是 FDE 产品公司，而是 AI 咨询公司。”

## 5. FDE 公司的价值链

可以把 FDE 拆成 7 层价值链：

1. 行业进入：找到有预算、有痛点、有数据、有决策人的场景。
2. 现场诊断：拆岗位、流程、系统、数据、审批、异常、责任。
3. 工作流建模：把业务流程改写成 Agent 可执行的任务链。
4. 数据与语义层：接入 ERP、CRM、文件、表格、聊天记录，建立权限和语义层。
5. Agent/系统交付：做工具调用、界面、日志、审计、人工兜底。
6. 运营与改进：持续观察错误、归因、人工介入点和 ROI。
7. 产品化抽象：沉淀成模板、模块、行业模型、平台能力或 SaaS。

最关键的是第 7 层。没有第 7 层，FDE 只是交付；有第 7 层，FDE 才可能成为高倍数 VC 可投公司。

## 6. 商业模式分类

### 6.1 高客单项目制交付

适合早期验证。按项目收取诊断、实施、部署、培训、运维费用。

优点：现金流快、客户需求真实。

缺点：人力绑定重，规模化差。

### 6.2 项目制 + 可复用模块

每个项目收费，但要求团队强制沉淀模块：

- 行业知识库模板
- 数据连接器
- Agent workflow
- 审计和权限组件
- ROI 看板
- 兜底和人工复核机制

这是最适合早期 AI FDE 初创公司的阶段。

### 6.3 行业 SaaS / Agent 平台

当某个行业的流程和客户需求高度相似后，转成产品化：

- 按席位
- 按流程量
- 按任务量
- 按结果 / 节省金额分成
- 私有化部署 + 年服务费

挑战：从项目制转产品化时，客户成功、销售、产品定义都要重建。

## 7. 投资和 FA 判断框架

### 7.1 先问“这是不是一个真 FDE 场景”

真 FDE 场景通常具备：

- 流程复杂，但不是完全不可标准化。
- 人工成本高，且可量化。
- 数据分散，但能获得授权。
- 客户有明确业务 owner，不只是技术试验。
- 交付后能影响收入、成本、风险、交付周期或合规结果。

伪 FDE 场景通常是：

- 客户只是想“接个大模型试试”。
- 没有生产系统接入。
- 没有可量化 ROI。
- 每个客户需求完全不同。
- 团队只能做 PPT 和 demo，不能承接生产责任。

### 7.2 再问“团队有没有 FDE 能力”

FDE 团队需要同时有四类能力：

- 工程能力：能接系统、写生产代码、做权限/日志/稳定性。
- Agent 能力：会任务编排、工具调用、记忆、评测、兜底。
- 行业理解：能在客户现场听懂业务语言。
- 商业交付：能收钱、控范围、做项目管理、逼出 ROI。

纯算法团队通常缺后两项；纯咨询团队通常缺前两项。

### 7.3 最后问“能不能产品化”

核心指标：

- 第一个客户到第二个客户，复用率能否超过 50%-60%。
- 交付周期是否从 8 周降到 4 周，再降到 2 周。
- 每个新增客户是否需要新增同等数量工程师。
- 是否形成标准报价、标准部署包、标准 ROI 报告。
- 是否能从“客户说什么做什么”变成“我们知道这个行业应该怎么做”。

1. 你们的长期记忆能力在 FDE 项目里具体解决哪个痛点？是客户流程记忆、用户画像、业务状态，还是 Agent 复盘？

4. 和 Mem0、Zep/Graphiti、Letta 相比，你们不可替代的地方是什么？
5. 如果 OpenAI / Anthropic / 字节做官方 Memory API，你们还剩什么防线？

### 8.4 团队和 FA 问题

1. 团队全职几人？创始人是否全职？学生身份和 IP 归属如何处理？
2. 技术第一作者是谁？商业交付负责人是谁？谁能去客户现场扛项目？
3. 目前是否已有付费客户？收了多少钱？客户愿意复购吗？

5. 未来融资叙事是“AI memory infra”，还是“传统行业 AI FDE/Agent workflow 公司”？二者如何统一？

## 9. 对隐迹智能的初步判断

基于现有材料，隐迹智能有两个叙事：

- 原叙事：AI Agent 长期记忆基础设施。
- 新叙事：进入传统行业现场，用 FDE 模式做 AI 工作流改造，再沉淀行业平台。

这个转向是合理的，因为纯 memory infra 赛道已经拥挤，且容易被大厂 Memory 能力 commoditize。FDE 方向能让团队更快接触真实业务、真实数据和真实付费。

但风险也很明显：

- 技术硬指标尚未独立核验，尤其是 LongMemEval SOTA。
- 团队是否具备客户现场交付能力未知。
- 从 memory infra 到传统行业 FDE，中间缺行业 know-how 和销售交付能力。
- 如果首个跨境电商/货代 case 没有可量化 ROI，就很难支撑 FA 融资叙事。

初步建议：WAIT，但值得约谈。约谈目标不是听 BP，而是验证“第一个真实客户 case 能否变成第二个客户可复用模板”。

## 10. 建议的调研路线

第一阶段：行业理解

- 研究 Palantir、OpenAI、AWS 的 FDE 定义和组织方式。
- 梳理 FDE 与咨询、外包、SaaS、AI Agent 平台的区别。

第二阶段：市场与竞品

- 海外：Palantir、OpenAI FDE、AWS FDE、Anthropic/Cohere 类似岗位。
- AI memory：Mem0、Zep/Graphiti、Letta。
- 国内：字节、智谱、腾讯等 Agent 平台内嵌能力；传统行业 AI 工作流服务商。

第三阶段：项目验证

- 核验隐迹智能 SOTA、团队、IP、客户。
- 拆第一个行业 case 的 ROI。
- 判断项目制交付到产品化的路径。

第四阶段：FA 判断

- 是否值得签独家 FA。
- 适合找哪类投资人：AI infra、企业服务、产业基金、政府引导基金、传统行业数字化基金。
- 融资叙事用 memory infra、FDE、行业 Agent 平台中的哪一个作为主线。

来源：`C:\Users\MS66\Downloads\第14位-LATRACE-赵翔.pptx`，共 14 页。该 PPT 是图片型幻灯片，已按页抽取到 `D:\项目调研\latrace_ppt_slides\slide-01.png` 至 `slide-14.png`。

### 12.1 项目一句话定位发生了强化

PPT 首页口径是：

> 让 AI 从热潮，落地为企业生产力。

这比原 BP 的“全模态长期记忆基础设施”更偏企业 AI 落地。PPT 把 LATRACE 从单点 memory infra，进一步包装成“AI 工作平台 + 长期记忆基础设施”的组合方案。

核心新口径：

- 前台：`Cosein AI 工作平台`，接入微信、飞书、邮件、Telegram、API 等成熟工作入口。
- 底层：`LATRACE Memory Infra`，把文本、音频、视频和业务事件沉淀为长期记忆图谱。
- 目标：让 AI 进入真实工作流，并把每次执行沉淀为可复用企业记忆。

### 12.2 他们对痛点的定义更接近 FDE

PPT 第 2 页提出：AI 很热，但企业仍缺真正的执行层。

三类痛点：

1. 工作入口分散：微信、飞书、邮件、Excel、行业系统并存，信息散落，难形成统一执行链。
2. 统筹依赖人工：老板和骨干反复在多个系统之间搬运信息、跟进客户、催推进度。
3. AI 用完即忘：多数产品只完成单轮问答，无法持续记住客户状态、历史决策和业务上下文。

PPT 的结论是：

> 中国 B2B 企业真正缺的，不是另一个更会聊天的 AI，而是一层能进入真实工作流、持续执行并沉淀状态的系统。

这非常适合作为 FDE 调研的核心判断：企业 AI 的难点不是“能不能答”，而是“能不能接入口、跑流程、留状态、复用经验”。

### 12.3 市场切口：从高沟通密度、可量化 ROI 的行业进入

PPT 市场页给出的切入口：

- 货代
- 跨境电商
- 律所

打法：

- FDE 先拿标杆。
- 再沉淀行业包。
- 路径为：付费部署 -> 订阅复制 -> 平台扩展。

PPT 还强调：

> 我们不是从通用 AI 切入，而是从高沟通密度、可量化 ROI 的工作流切入。

这个口径比“AI Agent + AI 记忆基础设施”的原叙事更可落地，也更符合 FA 对项目商业化的判断逻辑。

### 12.4 硅谷验证逻辑：先进入现场，再沉淀平台能力

PPT 第 4 页将硅谷代表公司作为验证样本，抽象为三步：

1. 进入现场：通过前置工程或深度实施，先解决真实业务中的关键任务与瓶颈。
2. 沉淀模型：把数据对象、流程规则、权限关系与业务语义抽象成可复用结构层。
3. 平台复用：将一次性交付沉淀为可复制的平台能力与行业产品，形成持续收入。

PPT 的关键句：

> 真正被验证的，不是某个功能点，而是“先落地、再平台化”的方法。

这句话可以作为和项目方沟通时的主轴：不要只问“功能做了什么”，要问“第一个客户沉淀了哪些平台能力”。

### 12.5 中国落地路径：接入成熟工作流，而不是替换旧系统

PPT 第 5 页的中国路径是：

- 不替换旧系统：先嵌入客户已经在用的沟通与业务入口，降低上线阻力。
- 先做高价值工作流：优先切入询价、报价、跟进、合同、客服等高 ROI 场景。
- 每次交互都沉淀：把客户状态、业务事件、决策过程与证据持续写入长期记忆。
- 项目最终交付行业包：每个项目覆盖目标，都逐步沉淀为更标准化、更具复用性的行业能力。

这是一个比“驻场做定制”更好的表述：他们想做“嵌入式 AI 工作层”，先接入口，再沉淀状态，再做行业包。

### 12.6 产品架构：Cosein 执行，LATRACE 记忆

PPT 第 6-8 页把产品拆成两层：

前台 `Cosein AI 工作平台`：

- 多模型调度与角色化 AI 员工。
- 工作流编排与业务协作执行。
- 接入现有工作入口。
- 支持私有部署与企业级运行环境。

底层 `LATRACE Memory Infra`：

- 多模态长期记忆：文本、音频、视频、业务事件。
- Graph RAG 检索与证据链。
- 业务状态追踪与时间线组织。
- 租户隔离、合规部署、后端记忆平台。

执行闭环：

1. 工作入口 / 当前输入。
2. Cosein AI 执行层。
3. Graph RAG 证据层。
4. Belief / 状态更新层。
5. 输出与记忆回写。

PPT 特别强调 LATRACE 不是普通 RAG：

- 普通 RAG：找回相关文本后直接生成。
- LATRACE：检索相关证据，更新业务状态理解，再驱动下一步执行。

这给了一个更清楚的产品差异：LATRACE 卖的不是“知识库问答”，而是“带状态更新的工作流记忆”。

### 12.9 商业模式：部署验证 -> 席位订阅 -> 行业复制

PPT 第 11 页给出的规模化路径：

1. 首个标杆部署：以前置工程快速进入真实场景，验证 ROI 与可付费性。收入结构为部署费 + 初始席位订阅。
2. 同行业复制：沉淀岗位配置、连接器、提示词包与工作流模板；部署周期缩短，交付成本下降。收入结构以席位订阅为主，轻配置为辅。
3. 平台化扩展：从单岗位到多岗位，从单流程到多流程；行业包复用，形成持续 ARR。收入结构为席位 + 行业包 + 扩展服务。

单位经济逻辑：

- 前置交付是产品化入口，不是终点。
- 复用流程提升毛利。
- 行业模板决定规模化效率。

这与 FDE 支持派观点完全一致，但也正好给出反向验证标准：要看他们第二、第三个客户能否真正降低交付成本。

### 12.13 下一次沟通建议改问法

不要再泛泛问“你们是不是做 FDE”。建议直接问：

1. 首个国际物流客户的合同、回款和验收节点分别是什么？
2. 客户现在每天有多少业务动作通过 Cosein / LATRACE 完成？
3. 你们帮助客户提升了哪个指标：报价速度、跟进率、转化率、人效、响应时间，还是客户覆盖数？
4. 如果复制到第二家货代公司，哪些东西不用重做？哪些必须重新做？
5. 当前 37,200 元项目的毛利如何？创始人投入多少人天？
6. 货代行业包 v1 具体包含哪些模板：连接器、流程、prompt、行业知识库、报价规则、客户画像、邮件模板还是记忆图谱？
7. 你们的长期记忆在销售工作流里创造的独特价值是什么？如果没有 LATRACE，只用普通 CRM + Agent workflow，会差在哪里？
8. 下一轮融资时主叙事到底是“AI 工作平台 + Memory Infra”，还是“货代/跨境电商 AI 员工平台”？

一句话结论：

LATRACE 的 PPT 把项目从“AI memory infra 技术项目”推进成了“以 FDE 方式切入高沟通密度行业、用 Cosein 执行层 + LATRACE 记忆层做企业 AI 工作流”的早期商业化项目。FA 价值在于帮助他们证明：首单不是一次性项目，而是一个可复制行业包的起点。
